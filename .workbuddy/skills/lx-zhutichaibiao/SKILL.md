# 按运营主体/城市/品牌拆表工具

将待拆表格按运营主体、城市或品牌维度拆分，保留原表单元格格式。

## 能力路由

拆分是核心功能，发布和通知是可选分支，可独立触发：

| 用户意图 | 触发词 | 对应阶段 |
|---------|--------|---------|
| 拆分表格 | 拆主体表、主体拆表、lx-zhutichaibiao、zhutichaibiao、按运营主体拆、按城市拆、按品牌拆、纯品牌拆 | **阶段一** |
| 发布到线上 | 发布、发布到飞书表格、推送到线上 | **阶段二** |
| 生成通知 | 生成通知、发消息给各主体、通知话术 | **阶段三** |

**典型流程**：拆分 →（可选）发布 →（可选）生成通知。但通知也可以不依赖发布，直接用缓存中的链接生成。

## 触发条件

拆分是核心触发条件，发布和通知为可选分支：

- **核心触发**：拆主体表、主体拆表、lx-zhutichaibiao、zhutichaibiao、按运营主体拆、按城市拆、按品牌拆、纯品牌拆
- **独立触发**：发布、发布到飞书普通表格、推送到线上（阶段二）
- **独立触发**：生成通知、发消息给各主体、通知话术（阶段三）

拆分完成后，询问用户是否需要执行后续可选步骤：
1. 「是否发布到飞书普通表格？」→ 是则进入阶段二
2. 「是否需要生成通知消息？」→ 是则进入阶段三

## 核心功能

### 拆分模式

| 模式 | 匹配条件 | 输出说明 |
|------|---------|---------|
| **运营主体** | 品牌+城市双条件 | 用 (品牌, 城市) 匹配运营主体，一个运营主体一个文件 |
| **城市** | 城市单条件 | 用城市匹配运营主体 |
| **品牌→运营主体** | 品牌单条件 | 用品牌匹配运营主体，一个品牌可能对应多个运营主体 |
| **纯品牌** | 品牌单条件 | 每个品牌独立输出，不映射运营主体 |

### 码表依赖

脚本通过 `lx_shujuku` 查询公司 dataReporting 的 `operator_brand` 表建立品牌+城市→运营主体的映射。运行前需确保 `config/fog_config.yaml` 的 `lx_shujuku.api` 段已配置 dataReporting 账号，并且 `lx_shujuku` 健康检查通过。

## 阶段一：拆分

### B 阶段目录与验收约定

当前版本沿用 `工作目录/输入/`、`输出/`、`原表存档/`、`处理日志/`；每次执行在输出下独占新任务目录，区分 `工作文件/`、`交付包/` 与本机审计。每个接收人独立 ZIP，只含该人的拆分数据工作簿；所有 `-k`/配置指定保留 sheet 均不交付，完整内容留在原表。未匹配报告、audit.json 和汇总日志只留本地，不能发给接收人。失败保留现场，不自动清理任何历史或本轮中间文件；归档只在日志及产物验收完成、无残留未处理内容且当前授权覆盖时执行，同名拒绝覆盖。任务 `ready.json` 是验收结束收据；仅有 ZIP 或 audit.json 不代表任务已通过，存在 failure.json 的任务先核清失败阶段。

### 执行前：交付范围与当前限制

按人交付要求：每个对接人的交付包只含其负责范围；完整源表及全部保留 sheet 仅留在操作者本地。此规则适用于已安装本版本实现的工作区，不授权删除或覆盖已有文件，也不意味着旧包或其他未提供本能力的工作区已经更新。

**当前实现：** 使用完整审计码表的行级关系，从源行按接收人及主体分组，逐人生成并读回 ZIP，不再把联合主体文件复制给多人，也不夹带原表/保留 sheet。合成回归通过不等于真实公司码表、目标 Excel 或其他版本已验收。范围无法证明时停止分发，不使用旧主体名单或一次性补救脚本绕过。目录与失败处理见 [使用说明](README.md)。

运营主体模式逐 sheet 要求品牌与城市，缺列不再自动回退；城市/品牌模式须按本次明确选择执行，已有的范围字段仍参与核对。纯品牌输出仅为本地品牌包，不能当作按人隔离交付。公式、数据区合并或跨表头合并无法正确保证时阻断该文件；输出为数据用 `.xlsx`，不复制宏或承诺完整工作簿功能。

源行、范围过滤、未匹配与展开输出分别核对，标准见本文“执行契约/验收”；操作解释见 [使用说明](README.md)。只生成 ZIP 不代表可以交付，单人筛选也不能证明多人包已经隔离。

### 步骤 0：检查配置（首次使用）

检查 `config/fog_config.yaml` 是否存在，并确认 `lx_zhutichaibiao` 段已配置。如需交互式补充，可运行：

```bash
python .workbuddy/skills/lx-zhutichaibiao/scripts/split_by_zhuti.py --config --confirmed
```

配置项包括：项目根目录、默认对接人、工作目录。每个用户维护自己的 `config/fog_config.yaml`，不提交到版本管理。码表来源固定为 `lx_shujuku.operator_brand`。

配置完成后继续后续步骤。

### 步骤 1：检查待拆目录和码表

检查工作目录下的 `输入/` 中是否有 Excel 文件（`.xlsx` / `.xlsm`），并确认 `lx_shujuku` 可从公司库加载 `operator_brand` 码表。任一缺失则报告并终止。

### 步骤 2：询问用户选择

**先明确以下参数，已有明确指令直接采用，只补问会改变结果的缺口：**

1. **拆分维度** — 选项：运营主体 / 城市 / 品牌→运营主体 / 纯品牌
2. **对接人范围** — 选项：默认（读取 config 中的"默认对接人"）/ 全部 / 指定对接人
3. **保留 sheet** — 确认哪些 sheet 不拆分；本轮全部留在本地原表，不再完整复制到交付文件

### 步骤 3：执行拆分

运行脚本（在 workspace 根目录下执行，无需 cd 到绝对路径）：

```bash
python .workbuddy/skills/lx-zhutichaibiao/scripts/split_by_zhuti.py -m <mode> -p <person> [-k <keep_sheets>] --dry-run
```

默认行为等同 `--dry-run`：只列出待拆文件，不创建目录、不连接公司库、不生成 Excel/ZIP/日志、不移动原表。确认输入目录、输出目录和源文件后，必须把 `--dry-run` 改为 `--confirmed` 才会连接公司库并应用拆分。两者互斥；`--config` 也只有配合 `--confirmed` 才会写配置。

参数说明：
- `-m`: 1=运营主体, 2=城市, 3=品牌→运营主体, 4=纯品牌
- `-p`: `all` 或逗号分隔的对接人中文名（如 `雷维亮`）
- `-k`: 逗号分隔的保留 sheet 名称（可选）

**注意**：如果缺少 `--mode` 或 `--person`，脚本会进入交互模式。应尽可能提供这些参数以非交互方式执行。

### 步骤 4：展示结果

报告拆分结果：
- 输出 ZIP 包路径
- 分文件数量和总数据行数
- 未匹配数据数量和原因
- 未匹配报告路径

读取本次任务 audit.json 的源行分类与展开关系、excluded_rows/excluded_sheets 的排除原因，以及 ready.json 的交付范围和整表状态。生成器已分别重新打开工作簿和 ZIP 核对值、表头、声明样式与关系数；真实任务仍按“执行契约/验收”复核实际范围，不从未匹配数反推过滤数，不把未知填 0。只有 target 范围完成但有未匹配/排除 sheet 时，报告部分处理并保留源表。

### 步骤 5：处理日志
任务在 `工作目录/处理日志/<任务标识>/` 生成 Markdown 格式的处理日志，记录：
- 处理时间和拆分模式
- 每个源文件的输出 ZIP、原表存档路径
- 各运营主体/品牌的数据行数
- 未匹配行数
- 汇总统计

日志在归档之前写入，源行与展开行分别报告。归档实际结果由输出任务的 ready.json 记录；归档或收据阶段失败时先看 failure.json 及源/归档现场，不能把命令失败理解为原表一定没有移动，不自动回滚或重跑。

### 步骤 6：询问后续操作

拆分完成后，**必须逐个询问**用户是否需要执行后续可选步骤：

1. 「拆分完成。是否发布到飞书普通表格？」→ 确认后进入阶段二
2. 「是否需要生成面向各运营主体的通知消息？」→ 确认后进入阶段三

用户可能只需要其中一项，或两项都不需要。

## 阶段二：发布到飞书普通表格

触发词：发布、发布到飞书表格、推送到线上。

同事共享流程统一由 `lx-nongfu` 编排，并通过 `lx-feishudocs` 写飞书普通表格。

### 前置条件

- 只选择 ready.json 中 `delivery_scope=contact` 的对应接收人包；核对本次主体/城市/品牌范围，不能上传整个管理端任务目录或 `local-only` 品牌包。
- WorkBuddy 已安装并绑定飞书连接器，`lark-cli auth status` 能看到正确飞书账号。
- 项目存在 `.workbuddy/skills/lx-feishudocs`。
- `config/fog_config.yaml` 中 `lx_feishudocs.spreadsheet_type` 为 `sheets`。
- 如需写入固定父目录，先配置 `lx_feishudocs.default_folder_token` 或业务侧目标 folder token。

### 共享发布流程

1. 拆分完成后，先把输出文件和目标 sheet 名交给 `lx-nongfu` 编排。
2. `lx-nongfu` 按运营主体确定目标普通表格和 sheet 名。
3. 写入前必须 dry-run，确认每个主体的行列规模、目标表格和 sheet 名。
4. 用户确认后，通过 `lx-feishudocs` 写入飞书普通表格。
5. 写入后再次读回验证，并把飞书普通表格链接用于通知。

普通表格 smoke 可先单独验证：

```bash
python .workbuddy/skills/lx-feishudocs/scripts/feishu_sheets.py smoke --dry-run
```

### 错误处理

- **未安装或未授权飞书连接器**：先运行 `lx-feishudocs` 的 `status` 或 `smoke --dry-run` 检查。
- **目标普通表格或 sheet 不存在**：由 `lx-nongfu` / `lx-feishudocs` 先创建或提示用户确认目标。
- **实体缓存缺失**：检查 `lx-feishudocs` 缓存或按飞书实际目录重新查询。
- **写入中途失败**：已完成的 sheet 不回滚，脚本输出各实体状态汇总。

## 阶段三：生成通知消息（可选，可独立触发）

触发词：生成通知、发消息给各主体、通知话术。

不依赖阶段一或阶段二。通知链接由 `lx-nongfu` / `lx-feishudocs` 的飞书普通表格提供。

发布完成后，用户通常需要将数据链接发送给各运营主体/商家。此阶段将平台发给内部的通知话术，转换为面向每个运营主体的个性化消息。

### 触发方式

1. **跟在阶段一/二后面**：拆分或发布完成后，用户提供平台原话
2. **独立触发**：用户随时说「生成通知」并提供平台原话，无需先拆分

### 消息转换规则

对每个运营主体，以平台原话为模板，做以下转换：

1. **不遗漏平台信息**：平台原话中的所有关键信息（背景、截止时间、注意事项等）必须保留，不可删减
2. **转换视角**：「内部协调」口吻 → 「对商家/品牌通知」口吻
   - 「辛苦大家同步确认招商」→ 「需要贵方招商确认」
   - 「请按照同步的司机明细给商家去提报」→ 「请按照同步的司机去提报」
3. **附加文档链接**：从飞书普通表格结果读取
4. **以运营主体名称开头**：明确标识这是发给哪个主体的
5. **人数按需添加**：仅在平台原话提及数量或有助于说明范围时附加，不做固定模板

### 数据来源

- 各运营主体的文档链接和名称：来自 `lx-nongfu` / `lx-feishudocs` 的飞书普通表格结果

### 消息示例

**平台原话：**
```
⚠️重要：二次分配信息同步
5月先锋司机选拔二次分配活动已下发，辛苦大家同步确认招商；
商家可提报司机明细如下，为避免重复提报，请按照同步的司机明细给商家去提报。
注：新司机体系1期4城及2期2城涉及司机不参与2次分配
招商&提报时间节奏：今晚22点前截止招商，明晚16点前截止提报司机明细
```

**转换后（拼哒出行为例）：**
```
【 拼哒出行 】
⚠️重要：6月生效先锋司机二次分配信息同步

5月先锋司机选拔6月生效，二次分配活动已下发，需要招商。

可提报司机明细见文档：https://example.feishu.cn/sheets/example_token

为避免重复提报，请按照同步的司机去提报。
注：新司机体系1期4城及2期2城涉及司机不参与2次分配
招商&提报时间节奏：今晚22点前截止招商，明晚16点前截止提报司机明细
```

## 执行契约

### 输入

- 动态枚举到的待拆表、拆分维度、目标 sheet/表头和 confirmed 后读取的公司库 `operator_brand` 码表。
- 可选飞书发布与通知阶段，以及各阶段的确认状态。

### 输出

- 分主体/城市/品牌文件、压缩包、未匹配报告和拆分统计。
- 每人独立 ZIP，仅含该人数据 `.xlsx`；完整源表、全部保留 sheet、审计与未匹配明细只留本地。纯品牌包标记 local-only，不能作为按人交付。
- audit.json 记录源行分类、展开关系和排除项，ready.json 记录本次任务完成/部分完成、包范围及实际归档位置；失败任务不产生成功收据。
- 可选飞书发布读回与通知草稿；不自动发送通知。

### 验收

- preview 下目标目录和源文件保持不变；confirmed 后按以下源行分类与输出关系分别验收，不要求输出行之和等于源行数。
- 源行身份为“源文件 + sheet + 原始行位置”；表头、空行和独立保留 sheet 分开统计，不按整行值去重真实相同行。待拆有效源行 = 目标范围内源行 + 其他对接人范围过滤行 + 真正未匹配行，三个集合互斥且完整。
- 按本次映射构造“源行 → 主体”的应有关系；按人交付时扩展为“源行 → 对接人 + 主体 + 适用城市/品牌”，逐项检查实际输出的遗漏、非预期重复与越界。一对多展开允许输出多于源行，文件夹名称不能代替范围证明。
- ZIP 可读且成员精确，逐文件/sheet 的表头、有效行、关键值及声明的字体/边框/填充/对齐/数字格式/列宽/表头合并均读回一致；全部保留 sheet 和完整源表不在交付包内。越界、遗漏与非预期重复均须为 0，未知不能记为 0。
- 本次完整码表证明、源行分类与实际产物读回证据齐备，且 ready.json 区分 contact/local-only 及整表/部分范围。成功处理原表可在存档定位；未匹配或未处理 sheet 存在则不归档。归档前失败保留输入与中间文件；归档已发生后的失败按源/目标实际状态处理，不虚称零移动，不为清空输入目录删除文件。
- 映射来自公司库码表；发布后读回目标，通知中的主体、链接和事实与拆分结果一致。
